Diagramas UML do STEAM Planner

Este documento reconstrói, a partir do código-fonte real do projeto, os quatro diagramas normalmente usados para apresentar a arquitetura de um sistema numa dissertação: casos de uso, componentes, sequência do fluxo principal e modelo de dados. Cada diagrama vem com uma leitura renderizada (Mermaid) e o código-fonte em PlantUML ou notação Entidade-Relacionamento, pronto para colar em qualquer editor UML e gerar a figura final.

Como este documento foi construído: mapeamento direto do código — rotas e páginas (src/pages), serviços de domínio (src/lib), Edge Functions e schema (supabase/) e o módulo de personalização (src/lib/machine-learning). Nenhuma informação aqui é hipotética.

01

Leitura para o texto: não existe um ator "Aluno" no sistema — o STEAM Planner é uma ferramenta de planejamento e apoio ao professor; o aluno participa apenas indiretamente, como destinatário do material impresso/exportado. O caso de uso de administração (UC13) não é uma aplicação separada: é um recurso condicional dentro do próprio Dashboard, liberado quando o e-mail do usuário consta na tabela app_admins.

02

Diagrama de componentes / arquitetura

Visão macro do sistema: cliente React, backend como serviço (Supabase) e provedores externos de IA. Não há servidor de aplicação próprio — toda lógica de servidor vive em Edge Functions.

Pontos a destacar no texto:

  • Não existe roteador de URL (react-router ou similar): a navegação é controlada por uma máquina de estados simples em App.jsx — relevante se a dissertação discutir decisões arquiteturais (SPA de tela única vs. multi-rota).
  • Chaves de API de IA nunca chegam ao cliente: toda chamada passa por uma Edge Function no Supabase, que guarda a credencial no servidor — arquitetura resiliente a vazamento de segredo pelo bundle do frontend.
  • A exportação de PDF não usa nenhuma biblioteca de geração de PDF: o sistema monta HTML e delega a impressão ao próprio navegador (window.print), o que simplifica a arquitetura mas depende do mecanismo de impressão do navegador do usuário.
03

Diagrama de sequência — geração de atividade com IA

O fluxo mais representativo do sistema: do clique do professor até o PDF impresso, passando pela seleção determinística de BNCC, a chamada ao provedor de IA (com fallback) e a validação/autocorreção antes da exportação.

PlantUML Ver código-fonte do diagrama de sequência 
@startuml
actor Professor as Prof
participant "PedagogicalPlannerModal" as Modal
participant "PedagogicalPlannerService" as Svc
participant "bnccSelector" as Bncc
participant "AIProviderManager" as Mgr
participant "Edge Function (gemini)" as Edge
participant "Google Gemini API" as Gem
participant "learningExperience" as LE
participant "ActivityViewer" as Viewer
participant "exportReport" as Exp
participant "Navegador" as Nav

Prof -> Modal : preenche wizard e confirma
Modal -> Svc : generateActivity(parâmetros)
Svc -> Bncc : selectBnccHabilidades()
Bncc --> Svc : habilidades BNCC reais (base offline)
Svc -> Svc : buildPrompt() com contexto e BNCC
Svc -> Mgr : request(prompt)
Mgr -> Edge : functions.invoke("gemini")
Edge -> Gem : generateContent()
Gem --> Edge : texto (JSON em markdown)
Edge --> Mgr : { content }
alt Gemini indisponível ou JSON inválido
  Mgr -> Mgr : aciona provedor de fallback (Cerebras)
end
Mgr --> Svc : texto bruto da IA
Svc -> Svc : extractJson / safeParseJson / repairJson
Svc -> Svc : applyOfflineBncc (valida códigos contra base offline)
Svc -> LE : normalizeLearningExperience()
LE --> Svc : atividade normalizada
Svc -> LE : validateLearningExperience()
Svc --> Modal : atividade pronta
Modal -> Viewer : exibe atividade gerada
Prof -> Viewer : clica em "Exportar / Imprimir"
Viewer -> Exp : openActivityPrintWindow(atividade)
loop até 3 tentativas
  Exp -> Exp : prepareExperienceForExport() valida e autocorrige
end
Exp -> Exp : buildActivityPrintHTMLFromExperience()
Exp -> Nav : window.open + document.write(html)
Prof -> Nav : Ctrl+P / Salvar como PDF
@enduml

Ponto central para a dissertação: a IA generativa nunca é a autoridade final. Ela produz um rascunho estruturado; toda validação factual crítica — códigos BNCC, coerência financeira quando o tema é educação financeira, formato de DOI/referências, completude do texto — é feita por regras determinísticas no próprio frontend, com até três tentativas de autocorreção antes de permitir a exportação. Isso é uma escolha de arquitetura relevante para discutir mitigação de alucinação em sistemas educacionais assistidos por IA.

04

Modelo de dados (Supabase / PostgreSQL)

O schema tem duas metades bem distintas: um núcleo pedagógico (projetos, BNCC, fontes acadêmicas, feedback) e um conjunto de tabelas ml_* de personalização. Por isso o modelo é apresentado em duas figuras, o que também favorece a legibilidade na dissertação.

As duas figuras usam notação crow's foot (padrão Mermaid/ER), diretamente aceita pela maioria dos editores e compatível com o vocabulário usual de dissertações. Os tipos text_array e PK_FK representam, respectivamente, colunas text[] do Postgres e colunas que são simultaneamente chave primária e estrangeira (ex.: app_profiles.id, que é ao mesmo tempo PK da tabela e FK para auth.users.id).

05

Notas para o texto do artigo

Achados do mapeamento que valem uma frase própria na dissertação — não são óbvios a partir dos diagramas sozinhos.

AchadoPor que importa
O módulo machine-learning/ não contém nenhum modelo treinado. É contagem de frequência (top-N), similaridade por cosseno sobre um bag-of-words hasheado (FNV-1a, 96 dimensões) e uma fórmula de score linear com pesos fixados manualmente. Nomear isso com precisão evita uma afirmação incorreta na banca sobre "uso de machine learning".
Arquitetura multi-provedor de IA com fallback automático. Gemini é o provedor primário; se falhar (erro de rede, JSON inválido, indisponibilidade), o sistema tenta Cerebras automaticamente — resiliência arquitetural que pode ser discutida como contribuição de engenharia.
Validação determinística sempre "por cima" da IA generativa. Códigos BNCC, dados financeiros e referências bibliográficas nunca são aceitos apenas porque a IA os gerou — são conferidos contra bases offline e regras de negócio antes de chegar ao professor.
Não há roteador de URL. Navegação inteira controlada por uma máquina de estados em App.jsx — é uma SPA de tela única sem deep-linking, relevante se a dissertação tratar de arquitetura frontend.
Exportação em PDF é impressão de HTML pelo navegador, não geração binária de PDF. exportReport.js monta HTML/CSS otimizado para impressão A4 e delega a conversão para PDF ao próprio navegador do usuário (window.print).
Painel administrativo é um recurso condicional, não uma aplicação separada. Vive dentro do Dashboard.jsx, liberado por checagem contra a tabela app_admins. Várias tabelas de métricas (app_metric_snapshots, app_usage_events) já têm RLS pronta para leitura por admin mas ainda não são consumidas por nenhuma tela — infraestrutura preparada para um painel futuro.
